# deactivation of blocked broadcast users (post-processing)

После завершения массовой рассылки администратор может проанализировать её результаты и деактивировать (перевести в статус `revoked` без физического удаления строк из базы) всех пользователей, которые заблокировали бота (`blocked`) или чьи чаты недоступны (`unreachable`).

## Архитектура и контракты

1. **Мягкое отключение (`revoked`) + снятие VPN-доступа**:
   - Подписка переводится в статус `revoked` (согласно принятой политике удаления в проекте).
   - Сублинк начинает отдавать `404`, а сам пользователь автоматически исключается из будущих выборок для рассылок (`subscription_status = 'active'` по умолчанию).
   - Сразу после отзыва выполняется депровижининг тем же путём, что и admin `/del`: привязки `subscription_nodes` помечаются `pending_remove`, затем вызывается `SyncSubscription`, который физически удаляет клиента с панели. Без этого ранее импортированный профиль продолжал бы работать, хотя ссылка уже отдаёт `404`.
   - Если немедленная синхронизация упала, подписка остаётся `revoked`, а строки `pending_remove` подхватывает фоновый `SyncPendingNodes` (ретраи с экспоненциальной задержкой).
   - БД-фаза (статус + `pending_remove`) выполняется для всех получателей; обращения к панелям за один прогон ограничены `maxImmediateSyncs = 25` — иначе callback администратора висел бы на медленной панели пропорционально числу заблокировавших. Остаток снимает фоновый воркер.
   - История, заказы и сами записи подписок полностью сохраняются в базе для истории и аудита.

2. **Частичные сбои**:
   - Метод возвращает `*DeactivationResult{Targets, Revoked, Failed}` и агрегированную ошибку (`errors.Join`) по неудавшимся пользователям: сбой одного получателя не отменяет обработку остальных, но и не маскируется под успех.
   - Администратор видит либо «✅ Выключено: N», либо «⚠️ выключено N из M, ошибок K: <причина>», либо «❌ Ошибка…», если не удалось выключить никого.
   - `subscription_revoked` пишется сразу после успешной записи статуса, до внешних вызовов: отзыв — уже состоявшийся факт, даже если депровижининг ниже упадёт.

3. **Повторная регистрация / ренимация**:
   - Если заблокировавший ранее пользователь решит снова написать боту или зарегистрироваться (`Create` / привязка триала), система корректно возвращает его подписку в активное состояние (`reanimateRevokedSubscription`), фиксируя событие в аудит-логе.

4. **Интеграция в интерфейс администратора**:
   - В карточке деталей завершённой рассылки (`/broadcasts` → 📋 Детали рассылки) при наличии заблокировавших или недоступных пользователей отображается инлайн-кнопка: **`🧹 Отключить заблокировавших`**.
   - По нажатию бот запрашивает подтверждение с точным количеством пользователей и кнопками `[ ✅ Да, выключить ]` / `[ ❌ Отмена ]`.
   - После подтверждения выполняется сервисный метод `DeactivateBlockedBroadcastRecipients(ctx, broadcastID)`, записывающий каждое отключение в `audit_log` (`subscription_revoked` с причиной `broadcast_<id>_blocked`).

## Применение в коде

- **Сервисный метод**: `SubscriptionService.DeactivateBlockedBroadcastRecipients(ctx, broadcastID)` (`internal/service/subscription_deactivate.go`).
- **Интеграция в боте**: `CallbackHandler` обрабатывает колбеки `broadcast_deactivate_prompt_<id>` и `broadcast_deactivate_exec_<id>` (`internal/bot/callback.go`).
- **Кнопка в отчёте**: `broadcastControlKeyboard` в `internal/bot/broadcast_report.go`.
