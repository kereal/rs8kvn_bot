# 29 июня – 5 июля 2026

**Подписка теперь может приходить откуда угодно: rs8kvn_bot подключает read-only источники и наводит порядок в документации**

За неделю — 32 рабочих коммита. Главный результат: к управляемым VPN-узлам добавился новый класс источников, а вся архитектура и инструкции синхронизированы с реальным поведением системы.

**Что изменилось:**

• **Новый тип узла `fetch`.** Это read-only HTTP-источник proxy-конфигураций. Он не создаёт и не удаляет клиентов в панели — только отдаёт данные по указанному URL. Такой узел удобно использовать для внешних провайдеров, готовых фидов и источников, которыми rs8kvn_bot не должен управлять напрямую.

• **Fetch-источник встроен в общий lifecycle.** Он проходит через ту же модель подписки и синхронизации, но без лишних операций управления клиентом. Для внешнего endpoint URL используется как есть — без автоматического добавления ID подписки.

• **Кэш подписки стал безопаснее.** При отзыве или удалении подписки subserver больше не должен продолжать отдавать старую конфигурацию из кэша. Для временных ошибок БД сохранён осторожный stale-fallback: лучше кратковременно отдать уже известные данные, чем разрушить кэш при transient-сбое.

• **Состояния и HTTP-контракты стали строже.** Неуспешные ответы upstream не попадают в агрегацию как валидные конфигурации; revoked/expired подписки корректно приводят к 404. Это уменьшает вероятность выдать клиенту неполный или уже отозванный доступ.

• **Документация прошла большой аудит.** В ней отражены multi-node flow, типы `3x-ui`, `proxman` и `fetch`, актуальные метрики, SQL-примеры и реальные этапы синхронизации.

**Самое полезное для интеграторов** — единый контракт узлов при разных возможностях: одни управляют VPN-клиентами, другие только поставляют конфигурации. Продукт становится открытым к новым источникам без потери контроля над жизненным циклом подписки.

Попробуйте подключить read-only источник в тестовой среде и поделитесь опытом. Реакция поможет понять, какие типы интеграций сделать следующими.
